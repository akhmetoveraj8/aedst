# Decisions: Server

Part of the [decisions index](/decisions). Status and verification legends are defined there.


| Decision | Status | Rationale | Revisit when |
|---|---|---|---|
| **PostgreSQL 19** replaces 18 (owner decision, 2026-11-21): `postgres:19` in Compose and `postgrestest`, `ghcr.io/cloudnative-pg/postgresql:19-standard-trixie` for CloudNativePG (there is no plain `:19` tag; the `-standard-trixie` tag was probed on ghcr.io, backups already go through the Barman Cloud plugin so the image needs no in-tree barman). 19.0 went GA on 2026-11-19 (postgresql.org `versions.json`) | Accepted (**UNVERIFIED**: no Docker on the authoring machine, so migrations, sqlc, River, squawk and PgBouncer were not run against 19; none of them states PostgreSQL 19 support yet) | Version policy: latest stable major | An integration run (`task check:full`) fails on 19: record the finding and go back to `postgres:18` until 19.1. An existing local Compose volume initialised by 18 will not start under 19: recreate it (`docker compose down -v`) or run `pg_upgrade`; a CloudNativePG cluster needs its documented major-upgrade procedure, never a bare image swap |
| Valkey (go-redis client, `AEDST_VALKEY_*`) replaced Redis; **cache and `redis_rate` only, never correctness** | Superseded (2026-11-18) by DragonflyDB, next row | Open licence; anything that must be correct lives in Postgres ([ADR-0010](/decisions/0010-caching-and-data-partitioning)). The correctness rule carries over unchanged | n/a |
| **DragonflyDB replaces Valkey** as the cache and rate-limit store (owner decision, 2026-11-18); the go-redis v9 client and `redis_rate` v10 stay, behind `internal/platform/cache` (renamed from `valkey`); variables `AEDST_VALKEY_*` become `AEDST_CACHE_*` (neutral, so a later store swap is not another rename), and the deprecated `AEDST_VALKEY_*` alias was removed on 2026-11-25 (`legacy_env.go` deleted); readiness check and alert renamed `cache` / `AedstCacheDegraded`; Helm `config.valkey` becomes `config.cache` and `secretKeys.valkeyPassword` becomes `cachePassword` (rename the Secret key `valkey-password` to `cache-password`, or set `secretKeys.cachePassword` to the old key name); image `ghcr.io/dragonflydb/dragonfly:v2.1.0` (registry-verified 2026-11-18) | Accepted (owner decision) | **Licence: DragonflyDB is BSL 1.1 (source-available, not OSI open source), accepted by the owner.** It is run unmodified as a separate service, never linked or redistributed with our code, and it holds only rebuildable data (cache, rate-limit counters), so a licence change cannot corrupt or strand anything: the limiter degrades to per-replica limits and the cache refills. The protocol is RESP, so an exit to another RESP server is an image and endpoint change, not a code change. UNVERIFIED: the licence's Additional Use Grant and change date for the release in use (read its `LICENSE.md`); the integration test `TestRateLimiter_AgainstRealDragonfly` (`-tags integration`, needs Docker) was written but not run where this was authored, so `redis_rate`'s Lua script against real Dragonfly is unproven until that test or CI has passed | The BSL terms change so our use (an internal cache, not a hosted database offering) is no longer granted; the Additional Use Grant or the project's licensing is read differently by legal; Dragonfly breaks `redis_rate`'s script or a go-redis feature we use; or the owner requires OSI-only licences (then change the image and `AEDST_CACHE_ADDR` to another RESP server) |
| **Meilisearch is the single search engine**, on top of PostgreSQL `pg_trgm` (owner decision, 2026-11-18). Port `internal/platform/search` (`Engine`), official client `github.com/meilisearch/meilisearch-go` v0.37.0 imported only there, indexing **only through River jobs** (`search.index`, args `(index, id)`, enqueued with `Indexer.EnqueueTx` in the write's transaction, worker reloads the row through the module's `Source`, so retries and reordering converge; never synchronous from a request). `pg_trgm` stays for simple substring and prefix lookups. Optional: `AEDST_SEARCH_URL` empty = off, no index jobs are enqueued, modules answer from `pg_trgm`. Image `getmeili/meilisearch:v1.57.0` (compose profile `search`; in Kubernetes run its own chart or a managed service and set `config.search.url`) | Accepted (owner decision) | One engine, MIT-licensed, typo tolerance and ranking that `pg_trgm` cannot give, single binary. PostgreSQL stays the source of truth and the index is rebuildable, so correctness never depends on it; an engine outage degrades search, not writes (readiness check `search` is optional). No module uses it yet: the first one registers a `Source` on `env.SearchSources` and calls `env.Indexer.EnqueueTx`. No full reindex job exists yet; add one with the first module that needs it | A second engine is proposed (reject: one engine), search must be strongly consistent with writes, or Meilisearch's single-node limits are reached (then Postgres FTS or a clustered engine, with a new entry) |
| **Feature flags: OpenFeature Go SDK + flagd** behind `internal/platform/flags` (`Flags`: `Bool`, `String`; both return the caller's default on any error), SDK `github.com/open-feature/go-sdk` v1.20.0 and provider `github.com/open-feature/go-sdk-contrib/providers/flagd` v0.8.1 imported only there (owner decision, 2026-11-18). Flag definitions live in Helm `flagd.flags` (rendered to a flagd ConfigMap; compose profile `flags` uses `deployments/docker/flags.flagd.json`); `AEDST_FLAGS_FLAGD_HOST` empty = every flag keeps its default. Tests use the SDK's in-memory provider. Image `ghcr.io/open-feature/flagd:v0.19.0` | Accepted (owner decision) | Vendor-neutral API, so the provider can change without touching modules; flagd is a small open-source service with file-based definitions that fit GitOps. **Flags gate rollout and operations only, never correctness or authorisation**: with flagd down the service runs on the code defaults. This is separate from the capability list `AEDST_FEATURES` that clients read (it describes what the server offers, not a rollout) | Targeting needs a managed UI or per-tenant audit (then another OpenFeature provider, same port), or flag evaluation shows up in latency profiles (then use the in-process resolver) |
| **ScyllaDB: recorded only, no code and no dependency** (owner decision, 2026-11-18) | Deferred | PostgreSQL covers every current workload. Take ScyllaDB only when **all** hold: a dataset is **write-heavy** (sustained inserts beyond what a tuned primary plus partitioning ([ADR-0010](/decisions/0010-caching-and-data-partitioning)) absorbs), it is naturally **partitioned by a key** and read by that key (time series, per-user feeds, event logs; no cross-partition joins or transactions), and eventual consistency is acceptable for it. It never holds the source of truth for money, identity or anything needing multi-row transactions. A new store needs its own entry, a platform port, a driver (`gocql`-compatible, to be chosen then) and a Library-First row: none of that exists today, and `go.mod`, `approved_modules.txt` and Compose carry nothing for it | A measured write-throughput or partition-size limit on PostgreSQL that partitioning, batching and a bigger primary do not fix |
| **Cache-aside is one in-house helper, `cache.Aside`** (`internal/platform/cache`): typed get-or-load with a TTL on every entry, invalidation by key and by tag (a version counter, O(1), no `SCAN`), one shared load per key (`golang.org/x/sync/singleflight`), Protobuf or JSON values, fail open on any DragonflyDB error or when no cache is configured, OpenTelemetry counters. First use: `GetTaskStats` (30 s TTL, invalidated by every task write in `tasks/module`) | Accepted (2026-11-21) | The Go cache libraries on top of go-redis (`go-redis/cache`, `eko/gocache`, `rueidis` client-side caching) each bring a second serializer or client, local in-process tiers that break invalidation across replicas, or no fail-open contract; the helper is about 200 lines over libraries already in `go.mod` and encodes the project rules (TTL mandatory, never correctness). Per-owner task counts were chosen because the dashboard reads them on every load, staleness is harmless and the invalidating writes are all in one module | A second store tier is needed, or a library offers the same fail-open and tag contract over go-redis |
| **Benchmark regressions gate on allocs/op, not time**: `task bench:check` compares the PR with its base using benchstat and fails on a significant allocs/op increase over 5% (or from zero); ns/op is reported only. benchstat is pinned by pseudo-version and run with `go run`, not added to `go.mod` or `mise.toml` | Accepted (2026-11-21) | Wall time on a shared CI runner varies by tens of percent, so a time gate either flakes or is too loose to catch anything; allocations are deterministic and are what most accidental hot-path regressions change. `golang.org/x/perf` has no tagged release, which the `go:` backend of mise and a `tool` directive handle less plainly than a pinned `go run` | A dedicated benchmark runner exists (then gate ns/op too) |
| **Slow-query reporting has three layers at 500 ms**: a pgx tracer in the server (`AEDST_DATABASE_SLOW_QUERY_MS`, log + span event + counter, statement text without arguments), `log_min_duration_statement`, and `auto_explain` with `log_analyze` **off** in CloudNativePG and Compose | Accepted (2026-11-21) | The database log has the plan but not the trace; the server knows the trace and the pool but not the plan. `auto_explain.log_analyze` instruments every statement, slow or not, so it is turned on only for a bounded investigation | Plans without timings prove insufficient in an incident (then enable `log_analyze` with `log_timing` off or a sample rate) |
| **k6 in CI: the smoke scenario is a gate, the load scenario is not**; the job needs an identity provider (`LOAD_OIDC_*` repository variables, client-credentials token) and reports that it skipped k6 when none is configured | Accepted (2026-11-21); UNVERIFIED, never run with a provider | A smoke run (1 VU, generous latency bounds, error rate, a minimum iteration count) fails only when the API is broken or grossly slow; arrival-rate percentiles on a shared runner are noise. The server issues no tokens (ADR-0019), so a load test without an IdP cannot authenticate and the old job could not even start the server | A dedicated load environment exists (then gate the load scenario there) |
| RedSync removed; Postgres advisory locks (`internal/platform/lock`) | Accepted | Redlock-style locks are not safe for correctness; Postgres is already the source of truth | A lock must span systems other than Postgres |
| NATS JetStream removed; integration events are **River jobs inserted with `InsertTx` in the producer's transaction** (one job per subscribed consumer; `internal/platform/events` `Publisher` + `Registry`, consumers are River workers, handlers idempotent, no inbox table); River is the single async mechanism (events and deferred jobs). **NATS JetStream is now used for one purpose: `internal/platform/natsbridge` forwards allowlisted events to the Rust gateway ([ADR-0021](../../../apps/server/docs/adr/0021-nats-jetstream-and-rust-gateway.md), 2026-11-18); Kafka stays out. Never publish from request handlers outside a transaction.** | Accepted (owner decision, 2026-10) | [ADR-0014](/decisions/0014-river-insert-tx-as-outbox) (supersedes [ADR-0011](/decisions/0011-outbox-relay-and-in-process-bus), which superseded [ADR-0004](/decisions/0004-nats-jetstream)); one mechanism to operate, no relay, bus or inbox to maintain | A consumer becomes its own service (add a broker adapter behind `Publisher`), or measured `river_job` churn from deliveries threatens the primary workload ([scaling](/server/scaling)) |
| Router: replaced by net/http ServeMux (owner decision); realclientip-go for client IP; rs/cors | Replaced | Fewer dependencies; Chi was only needed for probes/metrics/webhooks, RPC mounts via `mux.Handle`. Client IP uses a trusted-hop strategy, never blind `X-Forwarded-For`/`X-Real-IP` | Revisit if routing needs outgrow ServeMux patterns |
| Goose kept; one version table per module (`goose_<module>`); squawk migration lint (`task lint:migrations`); `sqlc vet` | Kept | Re-checked 2026-11-18: Atlas Community (Apache-2.0) keeps versioned and declarative migrations, but since v0.38 `migrate lint` is Pro-only (a basic rule set remains), the PostgreSQL analyzers (PG301-PG311) and `migrate drift` are Pro, priced per seat and per CI project; Goose + squawk gives free Postgres-aware lint. Per-module tables keep the modular monolith splittable | Atlas ships Postgres-aware lint and drift detection in its free edition |
| Server is an OIDC resource server (jwx v4 + `jwkfetch`, `AEDST_OIDC_*`, asymmetric-only allow-list). ZITADEL default (AGPL-3.0 core since v3: used unmodified as a separate service, no obligations on app code), Keycloak (Apache-2.0) the alternative for projects that ban AGPL, Ory not recommended. first-party authentication was removed in ADR-0019 (no password hashing, no token issuing; `AEDST_OIDC_ISSUER` required); no self-built MFA, recovery or social login | Accepted | `apps/server/docs/adr/0017-identity-provider.md`, `apps/server/docs/adr/0019-remove-first-party-auth.md` (in-repo paths, not docs-site pages) | IdP licence changes; a project needs something no IdP offers |
| ZITADEL operations contract: JWT access tokens only (an opaque token yields `auth.ErrOpaqueToken` plus a rate-limited warn log, not a silent 401); audience = project id via scope `urn:zitadel:iam:org:project:id:<projectId>:aud`; roles from `urn:zitadel:iam:org:project:roles` with project role assertion on, optionally restricted to one organisation by `AEDST_OIDC_ROLES_ORG`; service-to-service uses ZITADEL machine users (client credentials or JWT profile). ZITADEL shares the CloudNativePG cluster only with a **separate database and role**, connects directly (never through the transaction-mode PgBouncer Pooler). Optional official Helm chart for the IdP. Legacy password hashes can be imported (`deployments/zitadel/import-users.sh`, user ids preserved) | Accepted. `bootstrap.sh`, `import-users.sh` (argon2id + bcrypt hashes), roles/audience/`end_session`/refresh behaviour and the server `OIDCVerifier` verified on 2026-10-08 against ZITADEL v4.19.4 (release binary, no Docker; needs `ZITADEL_SYSTEMDEFAULTS_PASSWORDHASHER_VERIFIERS=argon2,bcrypt`; machine users carry roles only in `urn:zitadel:iam:org:project:<projectId>:roles`, so `AEDST_OIDC_ROLES_CLAIM` uses that claim). The compose `idp` profile, Helm chart and Login UI v2 are UNVERIFIED (Docker engine would not start) | Keeps identity data and load apart from app data, avoids transaction-pooling breakage, and lets the first-party path be deleted early ([ADR-0001](../../../apps/server/docs/adr/0017-identity-provider.md)) | ZITADEL gets its own cluster, or the IdP changes |
| Push: one canonical document, [Push notifications](/server/push), for device registration (Web Push subscription shape, FCM/APNs tokens), the payload contract and VAPID rotation; other docs link to it. The server holds a single VAPID key: a dual-key overlap is **not implemented** (rotation is a planned cutover with client resubscription) | Accepted | One place to keep current; the single-key limit is stated, not hidden | Dual-key rotation is implemented (per-device `vapid_key_id`) |
