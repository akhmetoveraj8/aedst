# i18n overview — per-module translations across all platforms

**Mandatory rule:** translations live next to the feature/module that owns
them, never in one global catalog. This is the module-boundary philosophy of
[library-first](/library-first) applied to strings: a module's translations are
part of that module, and adding a module means adding its own translation
files, not editing a shared mega-file. All four client platforms follow this;
the mechanism differs per platform because each uses its own platform-native
i18n system (platform API before custom code: no hand-rolled translation loader
anywhere in this repo).

## One JSON translation format on every platform (mandatory)

**Mandatory rule, applies to every app that shows text (Web, Android, Apple, Desktop, Gateway and any future client):** translations use **one shared JSON format**, and a translation file written for one platform must work unchanged on every other platform. A string is written and translated once; no platform keeps its own copy, its own key names or its own wording.

1. **One source file per module and locale.** `packages/i18n/<module>/<locale>.json` (`<locale>` is one of `en`, `ru`, `tg`, `uz`, `ar`; `common` is the app-shell module). The file is UTF-8 JSON, no BOM, keys sorted as written by the formatter, and it is the only place the text is edited.
2. **One key shape everywhere.** Nested objects, `camelCase` keys, `<section>.<key>` inside the module (`login.title` in `auth/en.json`). The module name is the directory, never repeated in the key. The per-platform key shapes in the table below (`auth_login_title`, `authLoginTitle`) are derived output, not hand-written.
3. **One placeholder syntax.** ICU MessageFormat: `{name}` arguments, `{count, plural, one {...} other {...}}` for plurals. Native syntaxes (`%1$s`, `%@`, `%lld`, `{}`) are produced by the generator, never written by hand.
4. **Tajik is `tg.json` in the shared files.** Web keeps `tj` only as its URL/locale identifier and maps it to `tg.json` (see the convention below).
5. **Platforms consume the same files.** Web loads the JSON directly (next-intl). Android, Apple and Desktop get their native resources (`strings.xml`, `.xcstrings`, `.po`) **generated** from the shared JSON by a build step, so the platform-native i18n API is still what the app calls (no hand-rolled runtime loader), but the generated files are never edited or hand-copied. A generated file that differs from its JSON is a CI failure.
6. **Adding or changing a string** means editing the five JSON files of the module once; all platforms pick it up. A string that exists on one platform only still lives in the shared module file, so another platform can adopt it without copy-paste.
7. **Gate.** `scripts/check-i18n-parity.mjs` (`task check:i18n`) checks the shared files (same keys, same placeholders in all five locales) and that generated native files match them.

**Migration status (honest):** every platform now consumes the shared files, with these exceptions. Web app, admin and marketing read generated copies in `apps/web/shared/i18n/catalogs` (Turbopack and the Docker image cannot reach `packages/`); Android `app-tv` has only a non-translatable string. Android `strings.xml`, Apple `.xcstrings` and Desktop `.po` are generated and committed (hand-written leftovers the format cannot express stay in `strings_local.xml`, `apple-local.json` and `desktop-local.json`). Where a key existed on several platforms with different copy, the shared (Web or earlier-migrated) wording won; `targets.json` per module records which platform uses which key, and a key listed for one platform only is a worklist item for the others. Verification: Android feature, app and core modules compile with the generated files (`compileDebugKotlin`); `assembleDebug`, Android tests and devices are UNVERIFIED; Apple was never compiled and no Rust toolchain was available for Desktop, so both are checked statically only (parity script, round-trip comparison with the old catalogs, every Slint `@tr` string has its msgid).

## Locales and the `tj` / `tg` convention

Five locales everywhere: `en` (English, the reference locale for parity and the
**default everywhere**: `defaultLocale` in `apps/web/shared/i18n/locales.ts`, Android's unqualified `values/` with `unqualifiedResLocale=en` in each app's `res/resources.properties`, Apple's development region), `ru`
(Russian), `tg` (Tajik),
`uz` (Uzbek) and `ar` (Arabic, right-to-left).

**Tajik code convention.** The canonical code is `tg` (ISO 639-1/BCP-47). The
only platform that uses `tj` is **Web**, as its internal locale identifier
(`locales.ts`, the `[locale]` URL segment, `i18n/tj.json` files); `tj` is
Tajikistan's country code and was kept on web to avoid renaming. Web converts
it to the real BCP 47 tag `tg` for `<html lang>`, `hreflang`, `og:locale` and
JSON-LD (`toLanguageTag`). Android (`values-tg`), Apple (`tg` in `.xcstrings`)
and Desktop (`i18n/tg/LC_MESSAGES/*.po` gettext catalogues) use `tg`. Rule: write `tg` in new docs, tooling and
native code; use `tj` only inside web. `scripts/check-i18n-parity.mjs` normalizes
`tj` to `tg` internally.

## Mechanism per platform

This table describes what the apps call at runtime and where the **current** catalogs are; the text itself comes from the shared JSON files above (target state, see the migration status).

| Platform | Mechanism | Where | Why this and not a library |
|---|---|---|---|
| [Web](/web/i18n) | [next-intl](https://next-intl.dev) JSON, one file per locale per module | `apps/web/shared/i18n/catalogs/<module>/{ar,en,ru,tg,uz}.json` (generated from `packages/i18n`), `common` for app-shell strings | Approved stack pick in library-first. |
| [Android](/android/i18n) | Android resource qualifiers: per-module `res/values*/strings.xml`. The unqualified `values/` is the default locale, **English**; `values-ru`, `-tg`, `-uz`, `-ar` hold the rest | `feature/<name>/src/main/res/values{,-ru,-ar,-tg,-uz}/strings.xml`, `app/` and `core/*/` for shared strings | This **is** the platform API; Android merges resources by name across modules at build time. |
| [Apple](/apple/i18n) | Xcode **String Catalog** (`.xcstrings`), one per feature (in its shared `<Name>Presentation` target, read by both UI builds) | `Features/<Name>/Sources/<Name>Presentation/Resources/Localizable.xcstrings` | Native since Xcode 15 (the repo targets iOS 18 / macOS 15); all locales in one JSON file per target. |
| [Desktop](/desktop/i18n) | gettext `.po` catalogs bundled by `slint-build`; `@tr("<module>" => "text")` in Slint (Rust + Slint, `apps/desktop`; the module is the msgctxt) | `apps/desktop/crates/<crate>/i18n/<locale>/LC_MESSAGES/<crate>.po` | Slint's own translation support. The English source text (msgid) is the key. |

## Cross-platform content consistency and key mapping

Web's JSON is the reference copy. Native platforms port key-for-key from it
when their feature reaches that screen, so all platforms say the same thing per
locale. When adding a user-facing string, write the copy once, translate it
into all 5 locales, and carry the same 5 strings into the other platforms'
catalogs as their features reach that screen.

Key-mapping convention, used by the parity script's `--cross` report:

| Platform | Key shape | Example |
|---|---|---|
| Web | `<module>.<section>.<key>` (module = i18n directory owner; `common` for app-shell) | `auth.login.title` |
| Android | `<module>_<section>_<key>` (snake_case, module-prefixed) | `auth_login_title` |
| Apple | `<module><Section><Key>` (lowerCamelCase, module-prefixed) | `authLoginTitle` |
| Desktop | English source text (gettext msgid; not comparable by name) | `Sign in` |

All three of the first rows normalize to the same lowercase `[a-z0-9]` string.

## Parity check

`scripts/check-i18n-parity.mjs` (`task check:i18n`, also a CI job in
`policies-ci.yml`):

- Within each platform, each bundle (web `i18n` directory, Android module
  `res/`, Apple `.xcstrings`, Desktop `.po` family per crate) must have the same keys in
  `en`, `ru`, `tg`, `uz`, `ar`, with the same placeholders (`{name}` ICU args on
  web, `%1$s` / `%d` on Android, `%@` / `%lld` on Apple, `{}` on
  Desktop). Reports missing keys, extra keys, placeholder mismatches and absent
  locale files. Exit code 1 on any finding.
- Desktop: an empty `msgstr` counts as missing.
- `--cross` additionally lists logical keys present on some of web / Android /
  Apple but not all (informational; `--strict-cross` makes it fail). Many web
  keys are legitimately web-only (admin console), so this report is a worklist,
  not a gate.
- `scripts/i18n-parity.allowlist` lists intentional exceptions, one per line,
  each with a reason. Do not use it to hide a translation gap.

Desktop (Rust + Slint) has one gettext bundle per crate with all five locales; the parity script reads the `.po` files directly. `{}` placeholders must appear the same number of times in every locale. Desktop is frozen, so these catalogs are kept in parity but not extended. The Android TV app module (`app-tv`) has no translatable string of its own (only the brand `app_name`); its screens use the five-locale catalogs of `feature/auth` and `core/ui-tv`, so the module is allowlisted.

## Locale scope and cost

Five locales are required everywhere by default: `scripts/check-i18n-parity.mjs` fails when any of `en`, `ru`, `tg`, `uz`, `ar` is missing a key. Each new string therefore costs five translations carried onto every platform kept by the product profile (the `core` profile keeps only web, which cuts the multiplier from four clients to one). A product that wants fewer launch locales must change the `LOCALES` list in that script, the per-platform resource lists and `features.yaml`, and record the decision in `docs/content/decisions/cross-cutting.md` with a "Revisit when". Arabic additionally needs a right-to-left review on every screen; do not drop it silently.
